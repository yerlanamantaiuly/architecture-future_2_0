# План управления рисками

Меры привязаны к ID из [risk-map.md](risk-map.md). Разделение: **технические** рычаги vs **управленческие**. Риск нельзя закрыть «ещё одним пайплайном», если нет владельца домена — и наоборот.

## Принципы

1. Пилот в 1–2 доменах (финрасчёты или пациентский поток) до масштабирования шины.
2. Совместимость с легаси — явный ACL, не «пока пишем в оба места без контракта».
3. Медицинские карты по умолчанию вне аналитики (deny by design).
4. Каждая мера имеет владельца: Platform / Domain / CISO / HR.

## Что нельзя закрыть одной техникой

- **O1, O4, O5** — без ролей, freeze Camel и квот ёмкости Mesh не случится, сколько ни поставь Kafka.
- **A3, A4** — юридическая модель согласия и запрет класса данных важнее любого DLP.
- **O3** — обучение; иначе платформа станет bottleneck из трёх человек.

## Что нельзя закрыть одним приказом

- **A1, A2, T2, T3** — нужны CDC, registry, DLQ, multi-AZ, иначе указ «переходим на события» развалится на первой схеме.
- **T1** — миграция с 2008 требует конкретного cutover, не дедлайна в презентации.

## Индикаторы, что план работает

| Индикатор | Пилот (6 мес.) | Масштаб (18 мес.) |
|-----------|----------------|-------------------|
| Доля новых интеграций через события, не Camel | ≥ 80% в пилот-домене | ≥ 80% критических доменов |
| Data products с DPO и SLO | ≥ 3 | ≥ 1 на домен |
| Отчёты витрины без класса `medical.*` | 100% | 100% |
| Dual-write новых фич в DWH | 0 | 0 |
| MTTD расхождения KPI batch vs stream | измерено | < 1 дня на разбор |
